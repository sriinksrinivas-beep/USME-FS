## Field operations — requirements & pain points (on-site walkthrough)
**Ground rules**: week1=current-state demo (process flows); week2=future-state gap discussion; Ascent preparing parallel process journeys. Focus ~90% common case, log exceptions separately.
**CEC** (Lisset Garcia): handles delivery/pickup/exchange, troubleshooting, pricing/inventory inquiries, inter-dept support, biomed depot-service requests, "Inside Sales" (no-warehouse corporate accounts) end-to-end. Sales Orders: reps quote, CEC submits/tracks post-signature. Main CEC workload = rental/pickup calls.
**GoUSME structure**: NO unified "order" object — tracked via **Call Logs** (delivery/pickup tickets w/ confirmation #). "Current Rentals" (account+modality) = status lookup, distinct from Call Log. CEC uses Partners (account lookup, Active-only, alert flags e.g. "BTS only"), Inventory (barcode lookup), Call Log. "Patient Transfer" exists but CEC doesn't use it (portal-only; CEC sends info to billing).
**Order intake**: caller name/dept/phone/email, modality (BTS=beds/patient-linked; MME=bulk/dept-linked, multi-item/qty). Mandatory fields vary per-hospital but CEC always asks patient info for beds + always captures height/weight/delivery location. Billing dept vs calling dept can differ (manual correction); idle equipment used by another dept needs post-hoc correction. Accessories = free-text notes only. Orders route via "service area" indexing (account→branch); branch manager manually assigns CSRs. Delivery defaults ASAP (~95%); earliest "future date" = next business day. Call Log: **Pending** (editable) → **Active** (locks, branch assigned/prepped).
**Gaps — inventory/substitution/consignment**: No real-time availability check at order entry. **Substitution governance (major, quantified)**: eligibility = model-level only, universal, no ranking; missing layer = account/contract-specific acceptance (tribal knowledge only — e.g. govt/VA contracts prohibiting substitution entirely, a CA correctional acct only accepting "Comfort 2"); real cost ~$97,000 billing nightmare from one improper substitution. Contract terms DO change over time (renegotiable) — needs maintainable rule set. No systematic pricing adjustment for substitutions (billing manually applies contract/list price); delivered model shows "substituted" flag, call log keeps original. **Pricing rule**: USME stock shortfall→original price honored; customer wants different model (exchange)→customer pays difference.
**Swap vs exchange**: Swap=same-model replacement, linked pickup+delivery, no price change; system can't substitute a different model within a swap (must cancel/redo as separate pickup+delivery). Exchange=customer wants different model, unlinked actions, priced for difference. Gap: swap pairs not visible in CEC back-office (no indicator without opening record); field/mobile DOES enforce pairing (can't complete delivery scan until pickup done) though invisible in admin views. Swap carries "reason" field (e.g. "PM due") to notify branches; unclear if tracked downstream.
**Billing start/stop**: deliveries=billing-start stamp, pickups=billing-end stamp, not manually chosen; pickup stamps at call-in (not physical collection), delivery stamps at actual completion; shows "expected" until confirmed.
**Consignment (gap)**: hospitals hold unused equipment, call to activate/deactivate billing. Needs contract approval (driver: delivery distance, e.g. 2-3hr each-way=~8hr shift). Gaps: (1) whole-account level only, not per-item; (2) no auto-standby — manual checkbox, forgetting causes incorrect billing from day one.
**Equipment failure/incident**: 3 categories needed — out-of-box (pre-use), on-patient w/harm (safety incident), on-patient no-harm (still reported to QA). "Performance form" exists (fields: presence at failure, property loss Y/N, injury/death Y/N+to whom, timing, free-text, replacement Y/N) but generic + entirely manual/outside system (emailed to clinician→QA, no link to order/item/rental, no history); chasing clinicians is a burden. Tied to ISO compliance push (standard unclear). CEC script: apologize/empathy/thank first.
**Field scan feature (major ask)**: scan unattended equipment → shows status (on-rent vs already-called-for-pickup), avoids duplicate pickups; close out+note damage on-site → better billing/damage docs. BTS scan surfaces whole patient-linked group; MME (bulk) harder to match serial to call-in. Root cause of missed call-offs: only one authorized person per hospital can call off-rent, relayed verbally (often dropped). MME partial returns often lack serial logging. Want: track last vehicle/CSR to have an item. Good existing feature to preserve: scanning one barcode from a bundle auto-adds related barcodes.
**Rental duration/dates**: MME bulk-order screen has no rental-period fields (gap). BTS pickup timing tied to patient care (no fixed date) but wants a not-to-exceed safety-net date (~"next PM date"). BTS benchmark: 3-7 days, USME's acute-care base mostly 4-7d.
**PHI field-access tension**: patient name/ID must stay protected, but field staff need some ID capability to match BTS equipment at delivery/pickup — reconcile with tokenization design (unclear ~10-15 day visibility-limit mentioned, unconfirmed).
**Documented pickup-attempt workflow (major ask)**: no systematic tracking today — want formal 3-attempt process (each documented/signed off, system prompts next attempt, after 3 failed→"lost"). Notification gap: no consistent alert to right contact on failed attempts. Triggers "equity buyout" (rental paid-to-date=equity, remainder owed, may be discounted); 30 days=threshold to drop a bill, documented attempts=audit justification.
**Reconciliation** (2-point, distinct from delivery): (1) Delivery—signature+scan, starts billing; (2) Pickup—ops manager reviews returns, confirms barcodes, reconciles to inventory; kitted items need full-component check. Whether delivery-side reconciliation should continue is open. Also wanted: field-level order reassignment (no desktop needed) and order-aging/SLA indicators in field app (neither exists).
**PM/compliance visibility gap**: no real-time notice during order-taking of upcoming PMs due, cert requirements, or workload-vs-capacity (e.g. "20 hours" example). MME units can go non-compliant while "on rent" with no return date ("infinity"), no system trigger. Disposables (e.g. straps) aren't returned, need separate billing/inventory tracking.
**Depot Services/Inside Sales/Sales Orders**: uses GoUSME+ServiceNow combo. A "case" can have ~20 case tasks, shipping from different branches, worked by biomed. Process: task template→select shipping→method (free or 3rd-party "hot shot" for large items).
**Parts/PO cancellation notification gap (major, biomed)**: if purchasing cancels a PO for a part tied to an open work order (e.g. manufacturer PO cancelled, or a transfer order cancelled because the source branch's system-shown inventory turns out wrong, e.g. Portland→Houston), there is NO notification to the technician — they simply assume the part is still coming; discovery is only reactive (technician checks back weeks later, or a team lead happens to monitor "work in progress" parts status). Suggested fix (from Bridge): on cancellation, the part requirement should automatically requeue for purchasing to handle (re-route to a transfer order or a different PO) rather than requiring the technician to manually resubmit the parts request. Described as "a huge gap" — any notification mechanism (e.g. in Salesforce) would help.
**Biomed technician work assignment**: uses weekly "production cases" (parallel structure to equipment-management/shipping cases), created week-over-week, assigning technicians work by model ID; completing work on a model fills that case's completion bar toward 100%. Distinct from "open work orders" submitted by the equipment management team (e.g. a $3,500 parts/work order) and assigned to technicians — these must be manually closed out by the team lead rather than auto-completing like production cases.
**Standard repair-time data gap**: standard labor-time/effort values for completing repair work exist per model + service-type combination (e.g. an infusion pump takes less technician effort than a ventilator) but this data is stored OUTSIDE the current system entirely (confirmed explicitly, not in ServiceNow/GoUSME) — relevant to production-planning/capacity commitments by branch criticality, which isn't systematically supported today.
**Action item**: USME's biomed/production-planning team (the people who plan technicians' weekly assignments) to send a "wish list" of process improvements/additions to Durvah (Srini/team) and Tom (Ascent) ahead of next week's deeper-dive session, so it can help focus that discussion in advance.
**Work order data model request (resolved)**: current system's Work Order→Work Order Task relationship is 1:1 (no multiple tasks under one work order), which USME finds redundant — they'd prefer a single work order with multiple sequenced lines instead of separate WO/WO-Task objects. Ascent confirmed their native model already works this way: a Work Order "header" with multiple "lines" (non-physical service/task lines plus physical lines like consumables), sequenced — satisfying this request natively.
**Inter-branch inventory allocation & reservation (major gap)**: Orlando=support center AND full branch. No reservation system — two coordinators can independently commit the same unit (manual Teams-message coordination only). Scenario: Phoenix/Orlando units for St. Louis order (Orlando picked); later Tampa order also defaults to Orlando (nearest) with no visibility it's earmarked — desired fix=visible reservation. Par levels ARE calculated (historical+recent demand) but NOT enforced against transfers. No reservation vs. known future orders either; affects "conversion stock" (staged 3-5wks ahead) which can be silently pulled for emergent needs — tradeoff accepted but visibility wanted. Allocation logic = tribal knowledge: geography/distance, financial sense of moving (value vs ease of shipment), contract obligation tier, and (manual) idle-vs-active equipment preference.
**Unit transfer**: billing-only transaction for patients moving between units — stops old unit billing, starts new unit next day, no delivery/pickup. Only some partners use it. "Transfer history" control shows changes. Available via portal (self-serve) or GoUSME (billing manual) — identical data either way. At pickup, system shows most recent location but staff must reconfirm verbally (equipment often moved to holding areas).
**Portal vs GoUSME gap**: portal lets partners self-update patient name/ID/PO numbers ("update details"); GoUSME has no CEC equivalent — biller must correct in back end.
**Technician-level reporting gap**: technicians want visibility into which work orders they've personally touched and what open parts requests they have (raised as a useful dashboard/report, not clearly available today).

## Invoice & tokenization architecture
- [stated] Authoritative records: Ascent=asset master/inventory/install-base/WO/billable events; GT=rate calc/invoice#/lines/credits/balance/payment status; SFDC=customer/contract/quote-order/patient-PHI/PHI-token map/invoice presentment&rendering/Files; Workato=orchestration only, never PHI/financial store.
- [stated] **Compliance boundary (confirmed live): neither GT nor Ascent is HIPAA compliant — ALL patient data stays solely in SFDC**; GT/Ascent only get opaque token/reference.
- [stated] Billing starts only on explicit rental activation; stop rule="pickup request date" (not physical collection, needs GT demo to prove); swap must not double-charge unless prorated; backdating needs approval; corrections(credit/void/rebill) happen in GT as events, prior SFDC docs superseded not deleted.
- [stated] Token creation (SFDC, on activation), 7 steps: validate customer/contract/order/episode/PHI complete → idempotency key → reuse active Billing Context if match → generate opaque token ("BCTX-" prefix) → transactional insert w/ retry → encrypt PHI, sharing, audit → publish tokenized event to Workato post-commit only.
- [stated] NOT every invoice line needs token — MME=bulk/no token, BTS=patient-linked/tokenized. GT never stores patient info, only resolvable reference.
- [stated] GT invoicing by order type: Sales (optional immediate-invoice flag), Rental (arrears via GT "bill cycle"), Services — GT owns timing/approval logic (customer-specific). GT has internal invoice-approval process (workflow TBD).
- [stated] Invoice rendering (SFDC, on GT's InvoiceFinalized event), 9 steps: GT sends event (header+line charges, NOT PDF) → Workato validates/upserts SFDC Invoice Presentment/Line via GT external IDs → confirm token resolves once, records match → pre-render reconciliation vs GT payload (no SFDC recalculation) → Queueable Apex invokes renderer → pulls approved PHI+immutable GT financials→PDF → SHA-256 hash+version+timestamp, ContentVersion linked → Document marked Current only after validation → internal(Billing Console)/external(Experience Cloud) access same doc under role/account auth.
- [stated] GT pushes to SFDC once approved; interface direction (push/pull/trigger) still undecided; Workato handles exception/failure reporting.
- [stated] Invoice files=SFDC ContentVersion/ContentDocument, version lineage explicit, no public links for PHI invoices; SFDC Files≠formal WORM archive — external archive needed if immutable retention required; proposed age-based archival pending SFDC storage-capacity numbers (unavailable yet).
- [stated] Invoice PDF format not required to replicate legacy GoUSME — decided separately; most fields non-PHI.
- [stated] Internal billing access via SFDC Billing Console (not Experience Cloud); billing users can request correction/re-render/dispute/GT credit-rebill but can't edit GT-derived amounts; hospital users see invoices via Experience Cloud only for authorized account/facility, never token values/other customers' data.
- [stated] Portal shows only preliminary running charge preview (excl. tax) — not final invoice; Durvah wants actual FINAL invoice viewable in portal too — GT to confirm feasibility.
- [stated] Credit memos created in SFDC (behind approval workflow) → sent to GT for actual credit invoice; must link to original invoice.
- [stated] Payments processed in Acumatica, sent to GT for AR only; GT will NOT send payment info back to SFDC — payment status for SFDC/portal must come from Acumatica (undesigned piece).
- [stated] Master data: customer master+product catalog mastered in SFDC, synced to GT; order info flows SFDC→GT; GT sources own tax/rate data; GT can share legacy schema as reference but redesign expected — full schema discussion needs Eric/IT. Unresolved: what master data GT itself stores & syncs.
- [stated] Shield/HIPAA: Shield alone ≠ compliance (also needs BAA services, access config, secured integrations, policies); key-mgmt approach & rotation/break-glass undecided; recommend parallel billing run before cutover.
- [stated] Illustrative tokenized event fields: eventId, eventType("RentalActivated"), eventVersion, eventTimestamp, correlationId, sourceSystem, billingToken, customerAccountId, rental order ID, productCode, ratePlanCode, quantity, serviceStart, currency — no free-text PHI. GT invoice numbers/IDs unique.
